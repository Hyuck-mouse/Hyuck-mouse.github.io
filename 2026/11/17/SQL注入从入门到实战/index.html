SQL 注入从入门到实战

Created2026-11-17|Updated2026-11-17|Web安全
|Post Views:

SQL 注入（SQL Injection）是最经典、也是危害最大的 Web 漏洞之一。本文把日常学习中零散的注入笔记整理成一条完整的学习路径：从判断注入点开始，到联合查询、报错注入、盲注，再到 sqlmap 自动化与请求头注入等进阶技巧。所有 payload 均来自实战靶场记录，可直接参考。

一、注入的基本流程

手工注入遵循一套固定的节奏，记住这四步，绝大多数注入题都能起步：

  1. 判断注入点：在参数后拼接 and 1=1、and 1=2，观察页面是否正常变化；或直接输入单双引号，看是否报错并回显 SQL 语句。
  2. 判断字段数：用 order by N 递增试探，直到页面报错，确定查询列数。
  3. 寻找回显点：union select 1,2,3,...，看数字在哪几个位置显示出来。
  4. 查询目标数据：结合 length()、substr()、group_concat() 等函数逐位提取，量大时交给 sqlmap。

五、布尔盲注

当页面只返回 true / false（有内容 / 无内容），既不回显数据也不回显报错时，用布尔盲注逐位猜解。

原理：构造一个布尔条件，比如 length(database())>1，若成立页面正常，否则异常；再配合 substr() 一位一位确定字符。这是一个纯逻辑推理过程，手工很耗时，通常直接用 sqlmap 或脚本跑。

补充：判断是否存在布尔盲注，就看页面是否会因条件真假产生稳定的两种状态（而非直接报错）。

六、quine 注入（自产生注入）

quine 注入是一种特殊场景：当 Web 认证要求**”前端输入 = 后端返回值”**时（例如密码校验处 $row['password'] === $password），普通联合注入拿不到 flag，就要让 payload 的输出与自身完全一致。

核心函数：replace(object,search,replace) 把 object 中出现的 search 全部替换成 replace。

七、请求头注入

注入点不只出现在 URL 参数里，HTTP 请求头的 Cookie、User-Agent、Referer 同样可能拼进 SQL 语句。

Cookie 注入

用 Burp 拦截请求，把带 Cookie 的完整请求保存成文本文件，交给 sqlmap：

注意把文本里的 id=XX 改成 id=XX*——星号告诉 sqlmap 注入点在哪，省去盲目探测的时间。

UA 注入

服务器会根据 User-Agent 返回不同页面，若 UA 被拼进 SQL，就形成 UA 注入：

  • level：检测等级 1~3，越高检查的请求头越多；
  • risk：风险等级 1~5，越高 payload 越激进。

实战中同样是把抓到的请求头存文件，把 UA 后的值改成 id=1*，再让 sqlmap 跑。

Referer 注入

Referer 是 header 的一部分，刷新页面时不会携带。此时用 HackBar 发一个带 referer 的 POST 请求 id=1，再把 referer 后的数据改成 id=1*，通过文本文件交给 sqlmap 查询数据库。

八、sqlmap 自动化

手工注入有极限——尤其时间盲注、布尔盲注需要大量爆破。sqlmap 五步走：

-r 从文件读取完整 HTTP 请求（适合需要登录态、或注入点在请求头的情况）；-u 直接指定 URL。两种方式每一步都能用，按场景选。同样记得把请求文件里的参数改成 id=XX* 来指明注入点。

小结

场景 适用方法 关键函数/工具
有回显位 联合查询 union select、group_concat()
无回显、有报错 报错注入 extractvalue()、updatexml()
只有真假状态 布尔盲注 substr()、length()
无回显无报错 时间盲注 sleep()、if()
输入=输出校验 quine 注入 replace()
注入点在请求头 Cookie/UA/Referer 注入 sqlmap -r
追求效率 自动化 sqlmap

注入的核心永远是”判断回显方式 → 选对提取方法“。把 payload 背下来不如把这套决策链记牢。

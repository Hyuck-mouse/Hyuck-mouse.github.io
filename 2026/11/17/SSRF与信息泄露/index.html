SSRF 与信息泄露：从 Git 泄露到 SVN 泄露

Created2026-11-17|Updated2026-11-17|Web安全

SSRF（服务器端请求伪造）让服务器替攻击者发请求，从而访问内网或本地资源；信息泄露则是配置不当导致 .git/.svn 等版本控制目录暴露，直接泄露源码。这两类漏洞都属于”低门槛、高收益”，是渗透测试必查项。

一、SSRF 基础

定义：SSRF（Server-Side Request Forgery）是一种安全漏洞，攻击者诱使服务器向内部或外部系统发起请求。由于请求从服务器内部发出，往往能绕过基于网络边界的访问控制。

二、SSRF 常见用途

1. 探测内网与本地服务

通过端口、路径探测服务器内网开放的服务。

2. 读取本地文件

利用伪协议：

3. 攻击内网其他服务

把服务器当跳板，攻击内网中有漏洞的服务，如：

  • Redis 未授权访问；
  • FastCGI 任意代码执行。

4. 云元数据服务攻击

访问云厂商元数据接口（如 AWS 的 169.254.169.254），获取临时访问密钥，进而控制云资源。

5. 访问内部系统

探测/访问服务器所在内网中不对外暴露的数据库、管理后台、元数据服务等。

6. 绕过防火墙

请求源在服务器内部，可绕过基于 IP/网络边界的访问控制策略。

SSRF 与 RCE 篇里的 “Ping DNS 外带” 是盲 SSRF 的典型数据外带手段，两者可对照阅读。

四、SVN 泄露：dvcs-ripper

成因：开发用 SVN 做版本控制并自动部署站点，若配置不当，.svn 文件夹会被直接部署到线上，造成 SVN 泄露。

流程：

  1. 用 dirsearch 或 nmap 扫描 URL 目录（.svn 接口不是 5XX 即可能有漏洞）。

  1. 扫描后 ls -al 看到 .svn 文件夹，进入后点 pristine（初始文件）目录，里面的文件（名字很长）用 cat 查看即可拿到 flag。

实战记录：pristine 下得到了 bf 和 cb 两个文件夹，最终在 cb 中找到 flag。

环境报错处理：

  • 报错1：Can't locate LWP.pm in INC（缺 Perl 模块）
  • 报错2：install_driver(SQLite) failed: Can't locate DBD/SQLite.pm（缺 SQLite 模块）

五、其他取证方向

早期笔记里还记了几个 MISC/取证方向（原为纯图片笔记，此处列提纲备查）：

  • 流量取证技术：pcap 流量包分析，提取传输的文件、明文凭据等。
  • 文件操作与隐写：文件头修复、附带数据、binwalk 分离等。
  • 图片隐写：LSB、Exif、像素域隐写等，常用工具 stegsolve、zsteg。

小结

漏洞 关键工具/协议 要点
SSRF file:///dict:///gopher:// 打内网、读文件、云元数据
Git 泄露 GitHack log/stash/index 三种恢复
SVN 泄露 dvcs-ripper .svn/pristine 找源文件
隐写取证 binwalk/stegsolve 分离文件、分析图片

这类漏洞的排查成本很低——扫一下目录、试几个伪协议，往往就能拿到突破口。做渗透测试时值得优先检查。

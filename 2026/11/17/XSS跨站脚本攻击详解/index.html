XSS 跨站脚本攻击详解

Created2026-11-17|Updated2026-11-17|Web安全
|Post Views:

XSS（Cross Site Scripting，跨站脚本攻击）是最常见的 Web 漏洞之一。攻击者把恶意 JavaScript 注入页面，当其他用户浏览时脚本在其浏览器中执行，可用来窃取 Cookie、钓鱼、记录键盘等。本文按”基础判断 → 三种类型 → 常用事件 → 靶场实战”的顺序梳理。

一、XSS 基础

成因

开发者习惯性地把用户输入不做任何处理直接返回到客户端，此时插入的恶意代码就会在页面上执行。

快速判断是否存在 XSS

  1. 找注入点：搜索框、留言板、注册项等一切用户输入会回显的地方，先插入 <script>alert(1)</script>。若弹窗显示 1，且查看源码发现 script 标签被原样输出，说明存在 XSS。
  2. 观察输出位置（决定 payload 怎么写）：
    • HTML 标签之间 → 直接写 JS；
    • 标签属性内、引号内 → 先尝试闭合引号，再构造事件；
    • 引号外 → 尝试构造新属性；
    • <script> 标签内部 → 引号内能闭合就直接写 JS，不能闭合就观察能否输出。
  3. 判断是否有过滤：是否被转义、关键字是否被拦。
  4. 构造 payload：结合输出位置选择闭合方式。
  5. 获取信息：Cookie、钓鱼页面、键盘记录等。

常用的 XSS 接收平台：xssaq.com。

二、三种类型

XSS 按恶意脚本的传递方式分为反射型、存储型、DOM 型。

反射型 XSS（Reflected XSS）

攻击者在输入字段插入脚本，脚本被服务器”反射”到响应中，在用户浏览器执行。需要诱骗用户点击构造好的 URL 才会触发，一次性、不落库。

靶场实战：

  1. 输入 <script>alert("XSS")</script>，若弹出 XSS 弹窗，说明此处有反射型注入。
  2. 从 XSS 平台复制代码到 name 框，提交后复制 URL。
  3. 把 URL 发给 Bot（或诱导用户点击），在 XSS 平台即可收到 Cookie / flag。

存储型 XSS（Persistent XSS）

恶意脚本被存储到服务器（如数据库），其他用户访问含该脚本的页面时自动执行。危害比反射型大得多——不需要诱导点击，所有访问者都会中招。

靶场实战：思路与反射型一致。插入语句后无回显（模拟黑客把 XSS 发到服务器），查看源码确认插入成功；再把 URL 编码后放到地址栏提交（模拟用户点开链接），在 XSS 平台查看收到的 flag。

DOM 型 XSS

前两种恶意脚本都会经过服务器再返回客户端，较易检测防御。而 DOM 型不经过服务器：恶意脚本在前端通过 JS 渲染完成数据交互，即使抓包也抓不到这段流量。

原理：DOM 把 HTML/XML 文档转成树形结构，脚本可操作页面各个部分。服务器返回的 HTML 里并不包含恶意脚本，脚本是在执行了一段”无害”代码后，被注入到文档里的——客户端 JS 动态修改页面节点，在本地执行。

事件 触发时机
onerror 标签加载资源出错时
onload 资源成功加载时
onmouseover 鼠标划过元素时
onfocus 元素获得焦点时（如 Tab 键选中）

小结

  • 反射型：脚本经服务器反射，需诱导点击，一次性。
  • 存储型：脚本落库，所有访问者中招，危害最大。
  • DOM 型：纯前端 JS 处理，不经过服务器，抓包看不到。
  • 判断流程固定：找注入点 → 看输出位置 → 判过滤 → 构造闭合 → 收信息。

防御侧的核心则是：输出编码、输入过滤、设置 HttpOnly Cookie（阻断 Cookie 窃取），以及部署 CSP。
